# 凌晨2点核心 API 告警，小李查到最后有点意外

## 故事背景
某个周二的凌晨 2 点多，小李睡得正香，手机突然响了。不是普通消息，也不是群里闲聊，而是值班告警电话。

电话那头的告警信息很直接：核心业务 API 检测失败，按照操作手册立即上报！听到这，迷迷糊糊的小李一下子就清醒了：凌晨 2 点，核心业务 API，检测失败。这几个词放在一起，能让任何一个 SRE 睡意全无。搞不好，这下来了一个大活！

小李赶紧爬起来，一边打开电脑，一边让自己清醒清醒，同时在脑子里快速过了一遍最坏情况：
- 是不是核心服务真的挂了？
- 是不是某个下游依赖不可用了？
- 是不是刚发布的新版本出了问题？
- 是不是用户请求已经开始失败，投诉已经在路上了？

小李先压住心里的紧张，开始按顺序确认：核心 API 到底是哪一段出了问题？

## 1. 第一反应：核心业务指标有没有异常？

小李先打开 Grafana，轻车熟路找到核心业务的 dashboard。接着他重点看了几个最关键的指标：
- API QPS: 每秒查询数量
- API 调用错误率
- API P95 / P99 延迟：95%/99% 的请求延迟
- API HTTP 5xx 错误率
- API 核心业务成功率

一番检查下来，图上并没有明显异常：核心监控指标即没有突降、也没有猛涨、指标的线条看着都挺平稳。小李看这结果有点奇怪。

他担心眼花了，于是又把时间范围拉长了一点，再次确认了一番。指标图是好的啊！QPS 没有掉下去，错误率没有升高，P95 / P99 延迟也没有突然拉长。核心业务成功率仍然保持在正常区间。

如果核心 API 真的不可用，这些指标里至少应该有一个会先露出马脚！但现在没有。

小李心里稍微松了一点儿，但还不敢下结论。因为有些问题并不会立刻体现在全局指标上。比如：
- 只有某个接口异常
- 只有某个参数组合异常
- 只有监控探测路径异常
- 只有某个机房或某个网络出口异常

所以这一轮检查只能说明一件事：核心业务整体看起来还活着。

但告警还在，事情还没个说法。小李决定继续检查应用日志，看看日志有啥线索。

## 2. 第二步：应用日志有没有异常？

接着，小李打开日志系统：Grafana Loki，开始查看应用日志。他先按服务名过滤，再把时间范围缩到告警触发前后的几分钟。

重点看几类日志：
- ERROR 错误日志
- Exception 异常日志
- timeout 超时错误
- connection refused 链接错误
- downstream failed 下游服务错误

结果还是正常：没有大面积异常堆栈，没有突然增多的 5xx 日志，也没有明显的下游依赖超时。

小李又把范围扩大了一点，看告警前后 30 分钟的日志趋势，依旧没有发现明显异常。

这时候问题开始让人困惑了：
- 告警说核心 API 检测失败
- 但业务指标正常
- 应用日志也正常

如果核心 API 真的出故障了，至少应该留下一点痕迹。可现在，系统看起来就像什么都没发生。

## 3. 第三步：人工手动测试 API
这时候，监控团队也提供了新的信息：他们用自己的测试账户手动测试了一下告警里的 API，结果看起来是正确的：

```bash
curl -i "https://api.example.com/core/health-check" \
  -H "Content-Type: application/json" \
  -H "authorization: Bearer <token>" \
  -d '{"key": "value"}'
```

返回结果看起来也没问题：
```text
HTTP/1.1 200 OK
Content-Type: application/json
{"status":"success","message":"query completed successfully"}
```

响应时间也正常。也就是说，从手动检查的角度看：
- API 能访问。
- HTTP 状态码是 200。
- 响应时间正常。
- 返回内容也不是空。

这就更奇怪了。如果业务指标正常、日志正常、手动测试也正常，那告警为什么还说 API 检测失败？

小李盯着屏幕看了一会儿，突然意识到一个问题：这个告警到底是怎么判断 API 失败的？

很快，小李的脑海就出现了构成告警的三个要素：
- 被监控对象
- 检测逻辑
- 触发条件

一个告警要想稳定运行，监控三角缺一不可。被监控对象自然是重中之重，但是也不能只看被监控对象，有时也要反过来看告警规则本身。现在不得不看看告警本身有啥线索了！

## 4. 拆开告警规则：它不是只看 HTTP 状态码

小李打开监控配置，开始看这条 API 检测规则。一开始他以为这条规则只是检查：
- HTTP status 是否为 200
- 响应时间是否小于阈值

但仔细一看，发现不是这么简单：这条检查除了访问 API，还会解析接口返回的 JSON，然后比较其中某个 key 对应的 value。

简化后的逻辑大概是这样：
```text
1. 定时请求核心 API
2. 检查 HTTP status 是否为 200
3. 解析返回 JSON
4. 取出某个 key 的 value
5. 把这个 value 和预期字符串做精确比较
6. 如果字符串不一致，就判定 API 检测失败
```

看到这里，小李大概明白了：如果只是检查 HTTP 200，那刚才人工测试已经能说明 API 是可访问的。但如果告警规则还要比较 JSON 里的字符串，那事情就不一样了。

因为字符串本身就比较脆弱，尤其是当它比较的不是一个稳定的协议字段，而是某个可能被业务版本影响的展示值、描述值、状态文案，或者拼接出来的字段。

## 5. 真相：API 没挂，返回字符串变了

小李继续翻最近的发布记录。果然，就在凌晨1点多，核心业务刚发布了一个新版本。这个版本没有改变 API 的 HTTP 状态码，也没有改变接口是否可用，更没有导致业务失败。但是，它改了 JSON 返回里某个 key 对应的 value ！！！

以前返回大概是：

```json
{
  "status": "success",
  "message": "query completed"
}
```

新版本返回变成了：

```json
{
  "status": "success",
  "message": "query completed successfully"
}
```

对业务来说，这两个返回都代表成功。但对监控规则来说，这两个字符串内容的不同就导致了检查失败。
```text
预期值：query completed
实际值：query completed successfully
比较结果：不一致
结论：API 检测失败
```

小李看到这里，终于把整条链路串起来了。
- 这不是核心 API 挂了。
- 这是监控规则把一个不该严格绑定的字符串，当成了 API 可用性的判断标准。

换句话说：服务没挂，业务没错，是监控规则太脆了。

## 6. 为什么这种告警容易误导人？

这类问题最容易坑人，尤其是大半夜的时候。因为告警名字通常写得很吓人：核心业务 API 检测失败

乍一看，像是核心服务不可用。但实际上，它可能有很多层含义：
- HTTP 请求失败
- HTTP 状态码不是 200
- 响应时间超过阈值
- 返回 JSON 缺少某个字段
- 某个字段的 value 不符合预期
- 返回内容格式变化

这些都可能被统一包装成“API 检测失败”，但它们的严重程度完全不一样。
- HTTP 请求失败，可能是真的服务不可用。
- 响应时间超时，可能是性能问题。
- JSON 字段缺失，可能是接口契约变化。
- 监控的字符串变化，则可能只是监控规则写得太死。

如果告警没有把失败原因说清楚，当值班 SRE 半夜被叫醒时，就只能先按最坏情况处理。

## 7. 临时处理：先让告警恢复正常
找到原因以后，处理就比较明确了。
- 短期先同步预期字符串，让告警恢复。
- 长期方案则提交到周会讨论：把完整字符串比较改成更稳定的判断方式。
例如：
```text
检查 HTTP status 是否为 200
检查 JSON 是否能正常解析
检查 status 字段是否为 success
必要时检查关键业务字段是否存在
```

调整以后，告警恢复正常。凌晨的紧张气氛也终于降了下来。小李看了一眼时间，已经快 3 点了。服务没挂，但人已经清醒了。

这可能也是 SRE 值班的另一面，也是最真实的地方：有时候你不是在修服务，而是在证明服务其实没坏。

## 8. 这次问题给小李的提醒
第二天复盘时，小李把这次问题归到了“监控规则脆弱”这一类：它不是业务故障，但它仍然值得认真对待。

作为告警三角之一的检测逻辑，必须要确保稳定可靠。如果告警规则依赖容易变化的字段，就很容易制造误报。如果误报多了，告警就容易失去信任，就很危险。

如果上升到信任层面，一旦真正的故障来了，大家可能会下意识觉得：是不是又误报了？这比一次凌晨被叫醒更麻烦。

小李给自己总结了几点：
1. API 可用性检查，优先看稳定信号，比如 HTTP status、响应时间、关键结构字段。
2. 不要轻易把展示文案、描述字符串、可变字段作为强校验条件。
3. 如果必须校验 JSON 内容，要明确这是“内容契约检查”，不要和“服务可用性检查”混在一起。
4. 告警信息要尽量说明失败原因，比如 status code 错误、JSON 解析失败、字段缺失、字段值不匹配。
5. 新版本发布如果会改变 API 返回结构或关键字段，监控规则也应该一起 review。

一句话，好的监控，不只是发现问题。它还要尽量准确地告诉你：到底是什么问题。
