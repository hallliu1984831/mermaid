# 拿来主义：我们为什么总在 Pull？

##  `pull`（拉取）
脑补几个大家都很熟悉的场景：
- 电脑（不管是 Mac 还是 Windows）提示系统要升级，更新器去下载补丁。
- 要安装一个软件，我们又去获取 RPM、DMG 或 EXE 安装包。
平时说起这些事，大家更习惯说“下载”；在开发和部署中，主动获取制品常被叫作 `pull`（拉取）。

除了升级系统、安装软件之外，码农要 pull 的东西还有不少，但 pull 这个动作却很相似。
- 修复一个 Java 依赖的安全问题，我们修改 `pom.xml` 中的依赖版本。构建时，Maven 如果在本地缓存里找不到对应的 JAR，就会去远端仓库取。
- 构建服务镜像时，Dockerfile 的 `FROM` 指向一个基础镜像。构建器可以复用本地已有的镜像；如果本地没有，或者构建时明确要求检查更新，就需要从镜像仓库获取它。
- 到了部署阶段，如果要使用远端仓库里的 Helm Chart，部署工具还得取得指定版本的 Chart。注意，取回 Chart 不等于应用镜像已经到了 K8S 节点上：Chart 和镜像是两种不同的制品。

## 这些动作有什么共同点？
文件可能是更新包、JAR、镜像，也可能是 Chart；发起动作的可能是 OS 的更新器、Maven、镜像构建器或 Helm。但它们有一个共同点：**需要使用制品的一方，主动向存放制品的地方请求并取回它。**

## 为什么要 Pull？
举个组装电脑的例子：我们不会先自己制造 CPU、内存和硬盘，而是挑合适的部件，组出需要的机器。做软件也很少从零开始。上游把成果做成更新包、JAR、基础镜像或 Chart；我们取回来，在它们之上继续工作。
**拿来主义很香，省下的正是重复造轮子的时间。**

## 拿来主义也会卡住
Pull 总是拿最新的吗？不一定。拿哪个版本，主要看版本声明；是否真的去远端取，还受本地缓存和工具的更新策略影响。比如 `pom.xml` 指定了某个 JAR 版本，Maven 不会因为仓库里有更新版就自动换过去。

另外，现成的东西也得拿得到。必须从远端获取时，仓库不可达、权限失效，或者指定版本不存在，都可能让构建或部署卡在拉取这一步。

所以下次看到“拉取失败”，先别急着查网络。先问清楚：**谁在拉？pull 什么？从哪里 pull ？** Maven 取不到 JAR、构建器取不到基础镜像、Helm 取不到 Chart，排查的仓库和执行环境都不一样。

## 一句话记住
Pull 是使用方主动取回现成制品，再继续构建或部署。拿来主义很香，但也要知道自己在拿什么、从哪里拿，以及拿不到时卡在哪一层。
